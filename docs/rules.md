# ResearchClawEval 科研 Agent 框架竞赛规则

本文件规定参赛资格、运行要求、提交格式与评分方法。赛后社区榜的扩展评测见 §1 和附录 A。

## §0 竞赛概述

比赛面向能够独立完成研究规划、代码实现、实验执行、结果分析与报告撰写的科研 Agent 框架，赛期一个月。

本仓库公开的三个任务仅供开发与自测，可重复运行和调试。正式测评采用其他任务，由主办方统一运行框架并评分。自测成绩不计入最终排名。

## §1 比赛与社区榜

| 项目 | 比赛 | 长期社区榜 |
|---|---|---|
| 周期 | 一个月 | 赛后持续开放 |
| 提交内容 | 框架源码与运行产物 | 运行产物及扩展评测所需记录 |
| 评测内容 | 正式任务的客观成绩与归一化总分 | 客观成绩、实验过程及 LLM 评审等 12 维指标 |
| 结果用途 | 确定比赛排名与总分冠军 | 持续展示框架评测结果 |

## §2 赛道与参赛

| 项目 | 规定 |
|---|---|
| 赛道 | 单赛道 |
| 参赛单元 | 一个科研 Agent 框架 |
| 任务 | 自测：`tdc_admet_tox`、`psydefdetect`、`arc_wbe_2026`；正式测评采用其他任务 |
| 提交内容 | 开源框架仓库与运行产物（§5） |

| 实验次数 | 2–4 条策略线，计数规则见 §5.8 |

公开任务的说明、数据获取方式和评分工具用于开发与调试，不得以自测结果代替正式成绩。

## §3 数据

本节说明三个公开自测任务的数据与切分。正式测评以对应任务的契约、预算和评分标准为准。

### 3.1 数据来源与许可

| 任务 | 来源 | 大小 | 许可 |
|---|---|---|---|
| `tdc_admet_tox` | Harvard Dataverse `doi:10.7910/DVN/21LKWG` V105 | 1.4 MB | Dataverse 条款 |
| `psydefdetect` | HuggingFace `AIMH/PsyDefConv` | 5.4 MB | `cc-by-nc-4.0` |
| `arc_wbe_2026` | HuggingFace `aicrowd/arc-whestbench-public-2026` | 907 MB | `cc-by-4.0` |

本竞赛按非商业用途举办。使用 PsyDefDetect 数据须遵守 `cc-by-nc-4.0`。

### 3.2 数据下载与校验

主办方不重新分发数据。参赛者通过以下脚本从原始发布处下载，并校验 SHA-256：

```bash
bash scripts/setup_datasets.sh --dataset tdc_admet_tox
bash scripts/setup_datasets.sh --dataset psydefdetect
bash scripts/setup_datasets.sh --dataset arc_wbe_2026
```

| 文件 | SHA-256 |
|---|---|
| `admet_group.zip` | `bd0005246cb6f1672333c28ad202112a8bf071ab65d847848715030308faf1f1` |
| `PsyDefConv.json` | `88d55e1ae6f4653661baa795166ef103f5439f4d6720b1767c3be7bbc3904ad7` |

若无法直接访问 `huggingface.co`，可设置 `HF_ENDPOINT=https://hf-mirror.com`。脚本仅在直连失败后启用镜像回退。

### 3.3 固定数据切分

主办方固定并公布各任务的数据切分及其 SHA-256。提交记录中的 `split_sha256` 必须与公布值完全一致，否则不予受理。

PsyDefDetect 采用对话级切分：训练集 1,875 条记录、160 个对话；评估集 461 条记录、40 个对话；两组对话无交集。该切分不同于数据集自带的记录级切分，后者可能在训练集与测试集中包含同一对话。

| 文件 | SHA-256 |
|---|---|
| `psydefdetect_split.canonical.json` | `2fa82b8f921bd135fb7c6e6dc4f97e95209c84f4613d402602e8cccb9942ccb9` |
| `tdc_admet_tox_split.canonical.json` | `83bc2a1b6c451adc7da1a31efd550388051abbc9cc912ff9328c9104c17a7ad7` |

ARC 的切分由 `setup_datasets.sh` 随数据集生成，不使用独立的 canonical 文件。可见验证集与评分集按 `mlp_id` 互斥，SHA-256 记录于 `<dataset root>/split_manifest.json`。

### 3.4 ARC 可见验证集

ARC 的评分集激活真值仅供主办方评分使用，不向框架开放。为支持实验比较与自评，100 个 MLP 中的 10 个组成可见验证集并提供真值，其余 90 个用于主办方评分。两组按 `mlp_id` 互斥，由 `setup_datasets.sh` 生成。

框架须在 `experiment_trace.json` 中以数值记录每次实验的 `n_mlps`、`adjusted_final_layer_score`、`final_layer_mse` 和 `all_layers_mse`。缺少数值化自评记录时，无法据此计算社区榜的 `b0`、`bT`。

## §4 模型

| 阶段 | 模型来源 | 要求 |
|---|---|---|
| 自测 | 参赛者提供 | 不限制模型选择；推荐 `deepseek-v4.1-flash`，不作强制要求 |
| 正式测评 | 主办方统一提供 | 通过 `OPENAI_BASE_URL / OPENAI_API_KEY / OPENAI_MODEL` 注入，框架不得另行指定模型或 API 地址 |

两阶段均须通过环境变量配置模型访问，代码不得硬编码 endpoint 或模型 ID。正式测评核对 `experiment_trace.json` 中的 `framework_internal_model` 和 `framework_internal_api_base_url`；与指定配置不符的运行不予受理。

模型 ID 区分大小写。配置错误可能返回 `no healthy deployments`；正式测评须使用主办方公布的完整 ID。

## §5 提交物

本节规定接入、自测和正式运行所需的记录格式。逐任务载荷以该次任务契约为准。公开自测产物不能替代主办方在正式任务上的运行结果。

### 5.1 框架仓库与适配器

提交开源框架源码与复现说明，主办方按 §7 审查源码。

提交前须校验适配器的 `manifest.json`：`python3 scripts/validate_schemas.py --manifest <manifest-path>`。必需字段与格式见 `schemas/adapter.schema.json`。`NN`、`replace-me` 等占位符仅允许出现在仓库自带的示例中。

### 5.2 运行产物

每个任务保留一份产物，目录结构如下：

```text
<framework>-<topic>-<YYYYMMDDTHHMMSS>/
├── PROVENANCE.json          # framework_commit / model / dataset_sha256 / split_sha256
├── workspace/               # 保留此目录名称
│   ├── research_idea.json   # 必需，首次实验前确定并锁定
│   ├── experiment_trace.json # 必需
│   ├── environment.json     # 必需，运行环境与复现信息
│   ├── final_report.md      # 必需
│   └── <topic 载荷>          # 见 §5.3
├── logs/
│   └── e2e.log              # 必需，运行时原始 stdout/stderr
├── prompt.txt               # 必需，workspace/input/prompt.txt 的原件
└── source/                  # 建议提供框架生成的研究代码
```

`environment.json` 须包含 `python_version`、`platform`、`device`、`seeds`、`packages` 和 `created_at`。

运行日志须保存为 `logs/e2e.log`。社区榜评审工具按 `logs/e2e.log`、`logs/native.log`、`logs/native_stdout.log` 的顺序查找日志，不读取根目录的 `run.log`。

### 5.3 任务载荷

以下格式适用于三个公开自测任务：

| 任务 | 载荷 | 格式 |
|---|---|---|
| `tdc_admet_tox` | `predictions.csv` | `sample_id,endpoint,probability` |
| `psydefdetect` | `predictions.jsonl` | 每行 `{"id":…, "predicted_label":…}` |
| `arc_wbe_2026` | `estimator.py` | 提供 `predict(mlp)`，返回 `(32,256)` NumPy 数组 |

### 5.4 运行器与预算

运行须采用官方 runner 模板生成的 `<framework>_<topic>_fullrun.sh`。模板与配置说明见 `scripts/runner/` 和 `docs/participant_quickstart.md`。

Runner 实时记录框架的 stdout/stderr 至 `logs/e2e.log`。主办方结合日志、原生执行标记、`PROVENANCE.json` 与实验轨迹核验运行记录。

运行预算按各任务契约执行。TDC 的累计实验预算为 3,600 秒，总墙钟预算为 7,200 秒；网络中断或网关波动不暂停计时，也不补时。PsyDefDetect 和 ARC 以各自 execution budget 为准，当前预算未规定墙钟字段。

自测前应通过小规模实验验证连接，并配置检查点、断点恢复和客户端重试与退避。注入的 relay 不提供统一重试配置；社区榜评审工具另有重试机制。

### 5.5 原生执行标记

`FRAMEWORK_NATIVE_LOG_MARKER` 须由框架自身的执行过程输出，不得由外层 wrapper 代为输出。标记应在运行早期记录；即使退出码为 0，缺少该标记仍判为非原生执行，不予评分。

检查命令：`bash scripts/check_native_marker.sh <run-root-or-log>`。第二个参数可指定自定义标记。

### 5.6 样本标识

TDC 的 `sample_id` 格式为：

```text
{endpoint.upper()}_{tv|test}_{归档行号}
```

`endpoint` 列中的 `hERG` 对应 ID 前缀 `HERG`，例如 `HERG_test_000000`。预测文件须直接使用 `public/test.csv` 提供的 `sample_id`，不得自行重建。ID 或 endpoint 不匹配时，校验或评分程序将拒绝该结果。

### 5.7 任务输入

Runner 根据任务契约、执行预算和任务摘要生成统一输入，挂载至 `$WORKSPACE/input/prompt.txt`。自测阶段通过 `PROMPT_TASK_SUMMARY` 或模板提供摘要，正式测评由主办方提供。

适配器负责将输入转换为框架支持的形式。提交的 `prompt.txt` 须为挂载原件，`prompt_sha256` 按该文件计算。

输入不得指定算法族、特征表示、模型架构、超参数、实验顺序或选定方法；这些选择须由框架完成。主办方按 `ideation_policy.forbidden_host_constraints` 核查，违反要求的输入不予受理。

### 5.8 实验计数：策略线

2–4 次实验按策略线计数，适用于树搜索等包含多个实验节点的框架：

- 一条策略线是一组实质性不同的实验配置，至少在算法族、特征表示、模型架构或超参数搜索空间的整体设定中有一项区别。
- 同一策略线内的重试、仅更换随机种子（seed-only repeat）或小幅调参不计为新策略线。
- 一条策略线须完成至少一个完整配置，即在固定验证切分上完成训练和评估，并生成指标与产物。
- 未完成训练或评估的环境配置尝试仅记入日志，不计入实验次数。已完成训练和评估后崩溃或超时的配置仍归入所属策略线；崩溃或超时本身不产生新策略线。
- 至少完成 2 条、最多开展 4 条策略线，不得开展第 5 条。

TDC 的墙钟与累计实验预算见 §5.4；其他任务按各自契约执行。

## §6 评测与排名

### 6.1 评测组织

主办方在正式任务上统一运行和评分。三个公开任务的自测成绩仅供开发与接入验证，不计入最终排名。不接受参赛者自报分数。

### 6.2 评分指标

比赛使用正式任务的客观评分。以下为三个自测任务的指标，供开发参考，不代表最终测评题目：

| 任务 | 指标 | 方向 |
|---|---|---|
| `tdc_admet_tox` | `macro_average_auroc` | ↑ |
| `psydefdetect` | macro-F1（正类 1–8） | ↑ |
| `arc_wbe_2026` | `adjusted_final_layer_score` | ↓ |

社区榜的七维 LLM 评审及 ED 不参与比赛排名，适用范围见附录 A。

### 6.3 排名

比赛设**总分冠军**，同时公布各正式测评 topic 的原始分、归一化分和单项排名。三个公开自测 topic 不参与总分计算。

#### 单项归一化

每个正式测评 topic 先换算成 0–100 分。主办方须在正式测评开始前公布并固定：指标及优劣方向、0 分参考值、100 分参考值、转换函数和单项计分精度。参考值不使用参赛队伍的最好或最差成绩，不随参赛队伍增减而变化。

设原始分为 `x`，0 分参考值为 `a`，100 分参考值为 `b`，转换函数为 `g`：

```text
s = 100 × clip((g(x) - g(a)) / (g(b) - g(a)), 0, 1)
```

`clip(z, 0, 1)` 表示将结果限制在 0–1。转换函数须在有效值域内严格单调递增，默认 `g(x) = x`；若指标需要对数转换，须提前公布转换方式及有效值域。`g(x)`、`g(a)`、`g(b)` 必须为有限值，且 `g(a) ≠ g(b)`；越高越好的指标要求 `g(b) > g(a)`，越低越好的指标要求 `g(b) < g(a)`。归一化后统一以分数较高者为优。原始分处于有效值域但超出参考区间时，归一化分限制在 0–100 分区间内。

这些是**正式比赛的计分参考值**，不直接沿用 `scoring/metric_anchors.json` 中为社区榜自测任务设置的锚点。正式 topic 的数值和转换方式以正式评分规则为准。

#### 总分与冠军

所有正式测评 topic 等权。设固定的 topic 数量为 `K`：

```text
总分 = (s₁ + s₂ + … + sₖ) / K
```

单项归一化分不提前舍入；总分统一四舍五入到小数点后六位用于比较。榜单可以展示更少位数，但展示舍入不改变排名。

1. 总分从高到低排名，第一名为总分冠军。
2. 总分相同时，比较单项第一的数量，更多者优先。
3. 数量仍相同则并列；榜首并列时为并列总分冠军。

单项第一按该 topic 的**有效原始分**、指标方向和公布的单项计分精度判定，不按封顶后的归一化分判定。单项并列第一时，每个并列框架各计一个第一；该 topic 没有有效结果时不产生单项第一。

#### 失败、缺项与资格

某个 topic 未通过准入、运行失败或缺少有效评分结果时，该 topic 对总分的贡献为 **0 分**，仍保留在固定分母 `K` 中，不得仅对成功任务计算平均分。保留失败状态，原始分记为 `null`，不得以原始分 0 替代缺失结果。只有通过准入、原始分有限且落在公布的有效值域内的结果才能归一化。

至少有一个有效正式测评结果的框架才能进入总榜；被取消资格的框架不参与排名和评奖。


## §7 方法独立性与源码审查

### 7.1 允许的开发活动

参赛者可在三个公开自测任务上重复运行和改进框架。正式测评采用其他任务，研究思路和实验方案须由框架根据任务输入自主确定。

### 7.2 禁止的任务适配

框架不得硬编码针对特定评测任务的方法或答案。任务名称、指标、数据路径等可通过输入和适配器传入，研究方法须由框架确定。

| 允许 | 禁止 |
|---|---|
| 按通用原则比较简单与复杂模型 | 预设分子任务必须采用 Morgan 指纹与 LightGBM |
| 对分类任务检查类别不平衡 | 根据 PsyDefDetect 的固定评估规模预设处理方案 |
| 使用通用实验设计原则 | 根据数据集名称或固定规模直接选择研究方法或输出答案 |

### 7.3 源码审查

主办方人工审查提交的源码。发现 §7.2 所列行为时，取消参赛资格。

## §8 不予受理的情形

| 情形 | 处理 |
|---|---|
| 缺少规定的运行产物 | 不予受理 |
| `dataset_sha256` 或 `split_sha256` 与公布值不符 | 不予受理 |
| `framework_internal_model` 或 API 地址与正式配置不符 | 不予受理 |
| `prompt.txt` 预先指定研究方法 | 不予受理 |
| 使用占位符或常量结果替代真实输出 | 不予受理 |
| 使用非官方指标或自报分数申请入榜 | 不予受理 |
| 命中 `forbidden_native_entrypoint_tokens`，如 `codex exec` | 判为非原生执行 |
| 违反 §7.2 的方法独立性要求 | 取消资格 |

不予受理或失败任务的总分贡献与资格处理见 §6.3。

## 附录 A：长期社区榜（12 维）

社区榜于赛后持续开放，沿用本仓库的运行与记录工具。任务与切分单独说明，三个公开自测任务不作为比赛的正式测评题目。

社区榜指标为 `b0 / bT / AUP / UR / ED`，以及 `PQ / PEA / ER / OU / ECC / SC / CC` 七维 LLM 评审。

### 适用范围与限制

- LLM 评审涉及额外调用成本和评分波动，不参与比赛的客观成绩排名。
- 评审工具优先采用执行日志；日志与报告或研究计划冲突时，以日志为准。
- 对参赛者自行运行并提交的日志，`ER`、`SC`、`CC` 反映提交证据所支持的执行情况，不能等同于主办方独立采集的执行记录。主办方正式运行采集的日志应与此类提交记录区分。
- `CC` 根据框架自身推导的义务清单评分，不能直接用于跨框架排名；跨框架比较需采用统一阶段要求，否则仅作展示。

### 指标记录要求

- `AUP` 存在 `1/N` 下界，不跨任务平均，报告时须同时给出实验数 N。
- `b0`、`bT` 使用 `scoring/metric_anchors.json` 的固定锚点归一化。这些数值为主办方约定的标定参考，不代表权威基线；引用时须注明。
- 社区榜锚点中的 0 表示随机水平，缺失指标须记为 `null`，不得以 0 替代。
- 评审模型在评测周期内固定并公布。
